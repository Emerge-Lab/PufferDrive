# Spline-Terminal-Boundary Action Mode for PufferDrive

## Context

Across the earlier discussion (imported from a prior chat, plus follow-up design turns), we converged on a specific idea for making the Drive policy's per-step control smoother and easier to credit-assign: instead of outputting raw jerk/steering each step, the policy predicts a **terminal boundary condition** — target position, velocity, and (optionally) acceleration a fixed horizon `T` ahead, per axis. A closed-form quintic spline is fit from the agent's known current state to that terminal condition, and the spline's *second derivative one raw step ahead* is used as the target acceleration for that step.

The key design result from this planning pass: this does **not** require a new "trajectory execution" subsystem. The env's `dynamics_model: jerk` path already does almost everything needed — persistent per-agent `accel_long`/`accel_lat` state, an `atan(curvature*wheelbase)` steering inversion, rate/position-limited steering, and exact-arc position integration, all already guarded against low-speed division issues. The spline mode only needs to replace *one* internal computation (how `a_long_new`/`a_lat_new` are derived before the existing clamp/integrate code runs) — everything downstream is reused verbatim. This means v1 is **receding-horizon by construction** (the spline is resolved fresh every raw step from the policy's fresh output; the agent never commits to executing the same curve across multiple steps, so decision points stay exactly where they are today). A later addition (the intent-consistency reward term, see Design decisions) does persist each step's solved curve coefficients as passive record for comparing consecutive predictions — but that's bookkeeping for a reward signal, not a change to control frequency: the policy still decides fresh every raw step either way. True multi-step commitment (executing one curve across `K>1` raw steps, changing decision frequency) and interruptible-option machinery are real, legitimate follow-ups but are explicitly deferred (see Out of Scope).

Goal of this plan: add `action_type: spline` end-to-end (C dynamics decode → Python action space/binding → policy head → training config), validated by new C unit tests, a Python smoke test, and a qualitative render comparison against the existing jerk+continuous baseline — with explicit attention to the one regime this codebase's maintainers are actively scrutinizing right now (low/zero-speed behavior, given the just-merged stop-sign logic in `dee651c8`).

## The mechanism, worked out: current behavior → proposed change

### 1. How `move_dynamics` works right now (jerk model), step by step

For a policy-controlled agent, every raw step (`drive.h:4339-4476`) does, in order:

1. **Decode the raw action into jerk.** Continuous mode: `j_long = action[0]` asymmetrically scaled to `[-15, 4]` m/s³, `j_lat = action[1]` scaled to `[-4, 4]` m/s³ (`drive.h:4351-4363`).
2. **Integrate jerk → target accel** (explicit Euler, one step):
   `a_long_new = agent->accel_long + c_throttle · j_long · dt`
   `a_lat_new = agent->accel_lat + c_steer · j_lat · dt`
   then clamp each to `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT`, with a "snap to exactly 0" rule if the sign flips across the step (`drive.h:4376-4393`).
3. **Integrate accel → target speed** (trapezoidal):
   `v_new = v_signed + 0.5·(a_long_new + agent->accel_long)·dt`, clamped to `[MAX_BACKWARD_SPEED, base_max_speed_mps]`, snapped to 0 on a sign flip (`drive.h:4398-4412`).
4. **Convert lateral accel → curvature → steering** (`drive.h:4422-4440`), this is the "GIGAFLOW" round-trip:
   `v_eff = max(|v_new|, 1.0)` — low-speed division guard
   `κ = a_lat_new / v_eff²`
   `δ_target = atan(κ · wheelbase)`
   rate-limit (`±0.6 rad/s`) and position-limit (`±0.55 rad`) → `δ_new`
   **then re-derive** `κ = tan(δ_new)/wheelbase` and `a_lat_new = v_new²·κ` **from the limited steering** — so the lateral accel actually applied is always consistent with the steering the vehicle can physically achieve, never the raw unclamped target.
5. **Integrate speed+curvature → position** via an exact circular-arc step, not Euler (`drive.h:4442-4456`):
   `d = 0.5·(v_new + v_signed)·dt` (trapezoidal arc length)
   `θ = d·κ`
   if `|κ| < 1e-5` or `|θ| < 1e-5`: straight-line fallback (`dx_local=d, dy_local=0`)
   else: `dx_local = sin(θ)/κ`, `dy_local = (1-cos(θ))/κ`
   rotate `(dx_local, dy_local)` from the agent's *current* heading frame into global, add to `sim_x, sim_y`; `sim_heading += θ`.
6. **Write back persistent state**: `agent->accel_long = a_long_new`, `agent->accel_lat = a_lat_new`, `agent->steering_angle = δ_new` — these three are read again as the starting point at step 2/4 of *next* step.

The only place this is jerk-specific is step 2 (how `a_long_new`/`a_lat_new` are produced *before* clamping). Steps 3-6 only ever consume `a_long_new`/`a_lat_new` as scalars — they don't care how those scalars were derived.

### 2. How we will change it: replace step 2's *source*, keep steps 3-6 byte-identical

Instead of integrating jerk, we solve a closed-form quintic spline from the agent's known current state to a policy-predicted terminal condition, and use the spline's predicted acceleration one step ahead as the new step-2 output. Concretely, per raw step:

**2a. Read the known starting state.** `p0_global = (agent->sim_x, agent->sim_y)` and `v0_global = (agent->sim_vx, agent->sim_vy)` are already in global frame — read directly, no conversion. `a0` is the one piece that needs a frame conversion: `(agent->accel_long, agent->accel_lat)` is **already stored in ego-frame convention** (§3 shows this precisely) — call this `a0_local`, to be rotated into `a0_global` in step 2c.

**2b. Policy outputs the full terminal condition in the same ego-local frame:**
`(p1_fwd, v1_fwd, a1_fwd, p1_left, v1_left, a1_left)`, raw ∈ `[-1,1]⁶`, rescaled per-axis by the derived offset limits (§ "How to set sane p1/v1/a1 offsets" — `p`/`v` limits derived from `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT`/`base_max_speed_mps`/`T`; `a1` reuses `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT` directly, no new constant) to physical local-frame values. **No jerk is ever decoded in this mode** — the policy never sees or produces `jerk_long`/`jerk_lat`; that machinery is simply unused for this action type, exactly the way the discrete-categorical machinery is unused when `policy.action_type: continuous` today.

**2c. Rotate boundary conditions into one consistent frame to solve the polynomial.** We solve in **global sim frame** (see §3 for why): convert `p1_local, v1_local` → `p1_global, v1_global` via the inverse of the ego-frame rotation (new helper, §3), and `a0_local → a0_global` the same way. `p0_global = (agent->sim_x, agent->sim_y)`, `v0_global = (agent->sim_vx, agent->sim_vy)` are already known — no conversion needed.

**2d. Solve the quintic, per global axis independently** (`x` and `y` decouple completely — this is a property of the polynomial parameterization, not of Cartesian vs. any other frame). With `c0=p0, c1=v0, c2=a0/2` fixed by the known current state, and `Δp = p1 - p0 - v0T - c2T²`, `Δv = v1 - v0 - a0T`, `Δa = a1 - a0`, the standard quintic terminal-BVP closed form (derived by elimination from the 3×3 system, verified below) is:

```
c3 = (10Δp − 4ΔvT + 0.5ΔaT²) / T³
c4 = (−15Δp + 7ΔvT − ΔaT²)   / T⁴
c5 = (6Δp − 3ΔvT + 0.5ΔaT²)  / T⁵
```

*(Derivation: substitute `A=c3T³, B=c4T⁴, C=c5T⁵` to turn the original system into `A+B+C=Δp`, `3A+4B+5C=ΔvT`, `6A+12B+20C=ΔaT²`; eliminate `A` then `B` to get `C = 6Δp−3ΔvT+0.5ΔaT²`, back-substitute for `B = −15Δp+7ΔvT−ΔaT²`, then `A = 10Δp−4ΔvT+0.5ΔaT²`; divide each by `T³/T⁴/T⁵` respectively. Verified by substituting back into all three original equations — coefficients of `Δp`, `ΔvT`, `ΔaT²` each check out to `{1,0,0}`, `{0,1,0}`, `{0,0,1}` respectively.)*

`a1` is a free policy output (per-axis, not fixed to 0 — see revised design decision below), so `Δa = a1 - a0` is used as-is, no simplification.

**2e. Evaluate only the second derivative, one raw step ahead**, in global frame, via `evaluate_quintic_derivative(coefs, dt, order=2)`:
`accel_target_global = (2c2 + 6c3·dt + 12c4·dt² + 20c5·dt³)` per axis — i.e. `a0 + 6c3·dt + 12c4·dt² + 20c5·dt³` since `2c2=a0`. For *control*, this is the only thing ever extracted from the curve — nothing about position, velocity, or the curve's shape beyond `t=dt` feeds into the executed command. (The full coefficients are, separately, persisted as passive record for the intent-consistency reward term — see Design decisions — but that doesn't feed back into control or change how often the policy decides; it's read-only bookkeeping for a reward signal.)

**2f. Rotate the target acceleration back into the agent's current heading frame** (reusing the *existing* `project_vector_to_ego_frame`, `drive.h:593-600` — no new function needed for this step, see §3):
`(a_long_target, a_lat_target) = project_vector_to_ego_frame(agent, accel_target_global_x, accel_target_global_y)`

**2g. Convert the target into an *implied jerk*, and clamp that to the existing physical jerk bounds — this is the step that guarantees every existing jerk/accel/velocity/steering limit still holds** (see "adhering to every jerk-based limit" below for the full reasoning):
```
j_long_implied = (a_long_target − agent->accel_long) / dt
j_lat_implied  = (a_lat_target  − agent->accel_lat)  / dt
j_long = clip(j_long_implied, JERK_LONG[0], JERK_LONG[3])   // same bounds real jerk actions already live inside
j_lat  = clip(j_lat_implied,  JERK_LAT[0],  JERK_LAT[2])
```

**2h. Fall through into the existing jerk branch completely unmodified, starting at `drive.h:4370`** — phantom-braking override, `c_throttle`/`c_steer` reward-coefficient scaling, `a_long_new = agent->accel_long + c_throttle·j_long·dt` (snap-to-zero + `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT` clip), the velocity/curvature/steering round-trip, the arc integration. From the moment `j_long`/`j_lat` exist, the spline path is indistinguishable from the discrete/continuous jerk path to the rest of the function — **no branch restructuring needed**, the spline decode is simply a third sibling way of producing `j_long`/`j_lat`, sitting where the existing decode (`drive.h:4341-4363`) sits today.

### 2½. Adhering to every existing jerk/accel/velocity/steering limit — not just accel and velocity

A polynomial being C² continuous *as a curve* says nothing about whether the *discretely re-solved, receding-horizon* target it produces changes gently step to step — each raw step re-solves the spline fresh from a fresh policy output, so nothing ties one step's implied acceleration to the next's. Left unfixed, this could produce accelerations that are individually within `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT` but that *jump* between those limits in a single `dt` — an effective jerk far beyond `JERK_LONG`/`JERK_LAT`'s actual range, defeating the entire smoothness motivation.

The fix (§2g/2h above) is to never let the spline's target acceleration touch the clamp/integration code directly. Instead, express it as a **jerk command relative to the agent's last known acceleration**, clamp that to the same `JERK_LONG`/`JERK_LAT` bounds the discrete/continuous action space already respects, and feed it into the existing formula unchanged. Every existing limit falls out of this for free, because from that point on the code path is byte-identical to today's jerk model:

| Limit | Enforced by | Changed for spline mode? |
|---|---|---|
| Jerk (`JERK_LONG`/`JERK_LAT`) | New clip on `j_long_implied`/`j_lat_implied` (§2g) | New, but reuses existing bound constants |
| Acceleration magnitude (`ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT`) | Existing clip, `drive.h:4376-4393` | No — untouched |
| Velocity (`MAX_BACKWARD_SPEED`/`base_max_speed_mps`) | Existing clip, `drive.h:4398-4412` | No — untouched |
| Steering rate (±0.6 rad/s) / position (±0.55 rad) | Existing round-trip, `drive.h:4428-4437` | No — untouched |
| Phantom-braking override | Existing check, `drive.h:4365-4368` | No — now applies to spline mode too, automatically, since it sits downstream of `j_long`/`j_lat` |
| `c_throttle`/`c_steer` domain-randomization coefficients | Existing multiply in `a_long_new`/`a_lat_new` formula | No — spline mode inherits the same per-agent randomization the jerk model already trains under |

The behavioral consequence: if the spline's terminal condition implies a large acceleration jump, the vehicle doesn't snap to it — it ramps at the same maximum physical jerk a real jerk action is limited to, converging over a few steps if the spline (re-solved fresh each step) keeps asking for it. This is the "safe degradation, not exact tracking" philosophy already stated elsewhere in this plan, now correctly extended to cover jerk, not just accel/velocity.

### 3. Global frame vs. agent (ego) frame — what they are, why both are used, and the exact math

**Global frame**: `agent->sim_x`, `sim_y`, `sim_vx`, `sim_vy` are all expressed here. It's a single shared Cartesian frame for the whole scenario, fixed orientation, origin at `Drive.world_mean_x/y` (`drive.h:211-212` — the scenario's centroid, subtracted from raw map coordinates at load time so `sim_x/sim_y` stay small, well-conditioned float32 values rather than raw UTM-scale numbers). Every agent's state lives in this one frame; it does not rotate or move.

**Ego (agent) frame**: a frame that *is* different per agent and *changes every step* — origin at the agent's current `(sim_x, sim_y)`, x-axis (`local_x`) aligned with the agent's current heading (forward), y-axis (`local_y`) perpendicular (left). This is not a new concept introduced for the spline — it's the exact frame the codebase already uses for observations: `write_reward_target_obs` expresses goal offsets in it, `write_partner_obs`/`write_road_obs`/`write_traffic_control_obs` express every partner/lane/stop-line position in it (all via `project_point_to_ego_frame`, `drive.h:584-591`). **Why**: two identical local driving situations at different absolute positions/headings in the world should produce identical (or near-identical) observations — global coordinates would force the policy to re-learn the same maneuver at every possible absolute position and heading it might occur at, a pure generalization tax with zero informational benefit. This is exactly the reasoning from the earlier design discussion (imported chat) about why ego-relative representation matters — it's not a new idea being introduced here, it's this codebase's existing, load-bearing convention, and the spline's policy I/O should use it for the same reason the rest of the observation vector already does.

**The exact rotation** (`project_vector_to_local`, `drive.h:558-568` — this is the ground truth, not a re-derivation):
```
local_x =  world_x · cos_h + world_y · sin_h     (world → ego, i.e. "project_to")
local_y = −world_x · sin_h + world_y · cos_h
```
This is rotation by `−heading` (cancels the agent's own heading out, so "forward" always reads as `+local_x` regardless of which way the agent is actually pointing in the world). `project_point_to_ego_frame` (`drive.h:584-591`) is the same rotation applied after translating by `(−sim_x, −sim_y)` first (points need translation, vectors — like accel or velocity — don't).

**The inverse (ego → world) is the transpose**, since a rotation matrix is orthogonal — **this does not exist yet in the codebase** (only the "to ego frame" direction is used today, for reading observations; nothing currently needs to go the other way) and is the one genuinely new piece of frame math this feature requires:
```
world_x = local_x · cos_h − local_y · sin_h
world_y = local_x · sin_h + local_y · cos_h
```
Two small new helpers, named symmetrically with the existing pair: `project_vector_from_ego_frame` (pure rotation, for `v1_local→v1_global` and `a0_local→a0_global`) and `project_point_from_ego_frame` (rotation + translation, for `p1_local→p1_global`).

**Why `(agent->accel_long, agent->accel_lat)` is already an ego-frame vector, with no conversion needed (a load-bearing fact for §2a/2c):** in `move_dynamics`, `a_long` is defined as accel *along current heading* and `a_lat` as accel *perpendicular to it* (`drive.h:4395-4396`, `heading_x/heading_y = cos_heading/sin_heading`) — that is definitionally `(local_x, local_y)` in the rotation above. The sign check: positive `a_lat` → positive `κ = a_lat/v_eff²` → positive `atan(κ·wheelbase)` steering → `sim_heading += θ` with `θ>0` → counterclockwise turn. Counterclockwise, in this codebase's `cos_heading/sin_heading` convention, is a **left** turn — and positive `local_y` in `project_vector_to_local` is also **left** (checked by plugging in `heading=90°`: a world-east vector, which is to the right of an agent facing north, maps to negative `local_y`). So `a_lat`'s sign convention already matches `local_y`'s sign convention exactly: **`(accel_long, accel_lat) ≡ (local_x, local_y)`, no sign flip, no new convention to invent.** This resolves most of the risk in the "sign convention" open item analytically — Phase B's unit test now exists to *confirm* this derivation empirically, not to discover an unknown from scratch.

**Consequence for step 2f above**: converting the spline's global target acceleration into `(a_long_new, a_lat_new)` is *exactly* the existing `project_vector_to_ego_frame` function, unmodified, applied to a new kind of vector (a predicted acceleration instead of an observed partner/lane position) — not a new "geometric curvature formula" and not a new projection helper. This is a real simplification over treating it as a from-scratch computation.

### 4. Observation array — does it need to change? No, and here's why

Checked `write_ego_obs` (`drive.h:3803-3819`, `EGO_FEATURES=10`, `constants.h:224`) against what the spline decode needs to know (`p0, v0, a0`) and what the *policy* needs to see to make a good terminal-condition prediction:

| Quantity | Already in obs? | Where |
|---|---|---|
| `p0` (current position) | Yes, *implicitly* — it's the origin of every ego-relative feature in the obs vector by construction, so the policy never needs to be told "where am I," only "where is everything else relative to me" | entire obs vector's frame convention |
| `v0` (current speed) | Yes, explicit | `obs[0] = sim_speed_signed / obs_norm_speed_mps` (`drive.h:3806`) |
| `a0` (current accel, both axes) | Yes, explicit, **already in the exact ego-frame convention §3 needs** | `obs[4] = accel_long/…`, `obs[5] = accel_lat/…` (`drive.h:3810-3811`) |
| current steering | Yes, explicit | `obs[3] = steering_angle/STEERING_LIMIT` (`drive.h:3809`) |

**Conclusion: no observation changes needed.** The C-side spline decode reads `p0/v0/a0` directly off `Agent` state (not off the observation vector — the obs vector is what the *policy network* sees, a separate data path from what `move_dynamics` reads), and the policy network already receives everything it would plausibly need to *decide* a good terminal condition (its own current speed/accel/steering, plus every goal/lane/partner/traffic-control feature already expressed in the same ego frame the spline's boundary condition will be interpreted in). This is worth stating explicitly as a non-obvious result: it would have been easy to assume the obs vector needs a new "current acceleration state" block for the policy to condition on — it's already there, added for the existing jerk-model comfort/steering bookkeeping, and it happens to be exactly what's needed here too.

### 5. How to set sane `p1`/`v1`/`a1` offsets (including turns)

These constants aren't safety-critical — the implied-jerk clamp in §2g/2h already guarantees safe execution regardless of how they're set. Their actual job is to make the policy's `[-1,1]` output range line up with what the vehicle can actually reach in `T` seconds, so exploration isn't wasted on infeasible asks. Derive each from limits the sim already enforces, plus `T`:

- **`a1_fwd`/`a1_left`**: no new constant — acceleration has an absolute physical bound regardless of horizon, so reuse `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT` directly (same asymmetric accel/brake scaling the jerk decode already applies).
- **`v1_fwd` offset**: `ACCEL_LONG_LIMIT[1]·T` (accel side), `|ACCEL_LONG_LIMIT[0]|·T` (brake side) — "how much can speed change in `T` seconds under max effort."
- **`p1_fwd` offset**: `base_max_speed_mps·T + 0.5·ACCEL_LONG_LIMIT[1]·T²` — a conservative upper envelope on distance traveled (uses max speed as a stand-in for whatever the current speed happens to be, so it's always generous, never too tight).
- **`v1_left`/`p1_left` offsets**: `ACCEL_LAT_LIMIT[1]·T` and `0.5·ACCEL_LAT_LIMIT[1]·T²`.

**Why this handles turns without special-casing:** every turn, everywhere on the map, is already bounded by the same `ACCEL_LAT_LIMIT` the rest of the sim uses. A sharper turn doesn't need a *larger* declared limit — it just spends more of that same fixed lateral-accel budget within `T`. The naturally small size of the lateral numbers relative to the forward ones (a car can't displace sideways nearly as fast as forward) is correct, not something to loosen. No per-scenario or per-curve-radius tuning is needed — computing these once from existing physical constants and `T` at env-init time covers every turn the policy will ever encounter.

## Design decisions (adopted, with rationale)

- **Single top-level on/off switch: `trajectory_training` (bool, default `false`).** Rather than exposing `action_type: spline` as a third value users pick alongside `dynamics_model`/`policy.action_type` (which is exactly the kind of independently-settable-knobs footgun already flagged for the existing `env.action_type`/`policy.action_type` pair), the feature is gated by one boolean, placed top-level in the config (sibling to `rnn_name`, since like `rnn_name` it's a cross-cutting switch touching both `env:` and `policy:`). `trajectory_training: false` (the shipped default) means config normalization never touches `action_type`/`policy.action_type`/`dynamics_model` — the env and policy behave bit-for-bit as they do today. `trajectory_training: true` is what actually activates the spline path internally. The internal `ACTION_TYPE_SPLINE` C constant and `"spline"` Python string from the rest of this plan still exist as implementation plumbing (that's what the C decode branch and the policy head key off of), but no user ever sets those directly — config normalization derives them from `trajectory_training`. This removes the cross-field footgun by construction: there is exactly one flag to get right, not three.
- **6-float policy output**: `(p1_fwd, v1_fwd, a1_fwd, p1_left, v1_left, a1_left)` — full position, velocity, and acceleration boundary conditions per axis, all policy-controlled. (An earlier draft of this plan fixed `a1=0` to cut policy-output dimensionality; reverted — the point of this mode is that the policy reasons in `(p,v,a)` terminal-condition space directly, not jerk, so `a1` stays free.) The action buffer widens accordingly wherever `4` appeared below (now `6`).
- **Purely continuous (Gaussian), never discrete, regardless of the default `policy.action_type`.** `trajectory_training: true` forces `policy.action_type = "spline"` internally (Phase A), which is a `Normal(loc, scale)` head exactly like today's `continuous` mode — completely independent of whether the *default* (switch off) policy is discrete-jerk or continuous-jerk. This was a real fork worth naming explicitly: a discrete head over 6 continuous dims would force an awkward choice between a combinatorially large joint categorical, a restructured multi-discrete (per-axis-independent-softmax) head, or throwing away dimensions to keep the class count small. None of that is needed — the spline mode simply never routes through the discrete-categorical machinery at all, the same way `continuous` mode doesn't today. Jerk itself (`jerk_long`/`jerk_lat`) is never decoded in this mode either — it's a full replacement of the action representation, not an alternative encoding of the same jerk actions.
- **Policy I/O in ego frame, polynomial solve in global frame** (see "The mechanism" §3 for the full derivation). Policy inputs/outputs are ego-relative (forward/left, heading-aligned) for the same generalization reason every other observation in this codebase already is — this does require a rotation, not just an offset (an earlier draft of this plan claimed otherwise; corrected). The quintic itself is then solved in global frame, since `Drive.world_mean_x/y` (`drive.h:211-212`) already keeps `sim_x`/`sim_y` small and well-conditioned, so no additional numerical benefit comes from solving in a rotated frame — only two small new rotation helpers (inverse of the existing `project_*_to_ego_frame` functions) are needed to move between the two, not a full transform subsystem.
- **Reuse the existing clamp/integrate code entirely unmodified — no refactor.** The spline decode is a third sibling path (alongside `ACTION_TYPE_DISCRETE`/`ACTION_TYPE_CONTINUOUS`, `drive.h:4341-4363`) that terminates in the same `j_long`/`j_lat` variables those paths already produce, then falls through into `drive.h:4370` onward completely unchanged. (An earlier draft of this plan proposed restructuring the branch so all three paths share a clamp block further downstream — unnecessary once the spline target is expressed as an *implied, clamped jerk* rather than a raw target acceleration; see "The mechanism" §2g/2h.) This is also what makes every existing jerk/accel/velocity/steering limit apply to spline mode automatically, not just accel-magnitude and velocity.
- **Safe degradation, not exact tracking**, is the explicit v1 philosophy: an infeasible spline target gets clamped by the existing `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT` exactly like an infeasible jerk command does today. No new hard SDF/feasibility filter.
- **Temporal consistency of *intent*, not just of executed motion — exact version, comparing predicted curves over their overlap, not raw outputs.** The jerk-clamp (§2g/2h) bounds how fast the *executed* acceleration can change step to step — it says nothing about whether the policy's *stated terminal intent* oscillates within that bound. This is the self-supervised consistency idea flagged (but not built) in the original imported chat that motivated this whole feature, now built in its rigorous form rather than the cheaper raw-output-diff approximation considered and rejected: comparing raw ego-relative outputs degrades exactly during sharp maneuvers (fast ego-frame rotation), which is when a consistency check matters most — comparing actual predicted **global positions** at shared absolute times avoids that entirely, since global frame doesn't rotate between steps.
  - **Mechanism:** curve solved at step `t` is valid over real time `[t, t+T]`; curve solved at `t+dt` is valid over `[t+dt, t+dt+T]`. Their overlap, `[t+dt, t+T]`, is interior to both (no extrapolation). At each raw-step-aligned offset inside that overlap, evaluate both curves' global position and accumulate the squared difference; scale by `reward_coefs[REWARD_COEF_TRAJECTORY_CONSISTENCY]`.
  - **Storage — 24 floats, not 12:** `compute_rewards` runs after `move_dynamics` each step and needs *both* curves at once, so both a `curr` and a `prev` full coefficient set (`c0..c5` per axis, i.e. 6 floats × 2 axes × 2 sets) must persist simultaneously — new `Agent` fields `spline_coefs_x/y[6]` and `prev_spline_coefs_x/y[6]`, rotated (`curr → prev`) only after `compute_rewards` has used both this step. Plus a one-bit `spline_history_valid` flag to skip the term on the first step after spawn/reset (no previous curve yet).
  - **Required helper split:** the earlier single "solve and immediately extract one derivative, discard the rest" helper no longer fits, since coefficients must now persist. Splits into `solve_quintic_coefficients(p0,v0,a0,p1,v1,a1,T) → (c3,c4,c5)` (the solve) and a generic `evaluate_quintic_derivative(coefs, t, order) → float` (reused for the order-2/`dt` control extraction in §2e *and* the order-0 sampling here).
  - **Bounded sampling loop, new `Drive` field:** number of samples ≈ `(T−dt)/dt`, computed once at env-init as `env->spline_consistency_num_samples` (not per-step), validated against a cap (fail-fast if `T`/`dt` implies an absurd sample count) — the loop itself lives in a new helper, `compute_spline_consistency_cost(...)`, called from `compute_rewards`, keeping `move_dynamics` itself dynamics-only (per this codebase's "one function, one subsystem" rule — the comparison is reward logic, not dynamics, even though the coefficients it reads were produced by dynamics).
  - Kept as a reward term specifically so `pufferl.py`/`pytorch.py` stay untouched — an auxiliary Python-side loss would require the PPO objective to special-case spline mode.

## Explicitly out of scope (flagged for a separate future decision, not built here)
- Multi-step SMDP commit / replan-every-K raw steps (needs a step-in-segment counter and changes step-loop/decision-frequency semantics — a materially bigger, riskier change than this plan makes. Note this is distinct from the stored curve coefficients added for the intent-consistency reward term above: those persist purely as passive record for a same-step comparison, and the policy still decides fresh every raw step either way; true SMDP commit would mean *executing* the same curve across multiple steps, which nothing here does).
- Interruptible/early-termination options (moot until multi-step commit exists).
- Hard SDF/drivable-area feasibility filtering, or curvature/jerk hard-rejection beyond the existing clamps (v1 relies entirely on existing `ACCEL_LONG_LIMIT`/`ACCEL_LAT_LIMIT`).
- A discrete/categorical spline head (joint grid over binned `p/v/a` axes, or a factored multi-discrete head). Not needed for v1 since the spline mode is purely continuous regardless of the default policy's discrete/continuous setting (see Design decisions) — noted here only because it was seriously considered and rejected, not because it's a planned follow-up.
